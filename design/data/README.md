# 기획 데이터 표

엑셀로 열어 고치는 표 모음이다. 지역, NPC, 교환, 아이템, 가보, 보스 같은 **목록형 기획은 여기가 원본**이다. 기획 문서(`design/gdd/`)는 큰 방향과 이유를 적고, 구체적인 목록은 이 표들을 가리킨다.

## 파일

| 파일 | 한 줄이 뜻하는 것 |
|---|---|
| `regions.csv` | 지역 하나 (계절, 색, 랜드마크, 가보, 보스, 귀한 열매, 구역 이름) |
| `npcs.csv` | NPC 한 명 (종족, 성격, 역할, 호감 축, 미니게임, 아빠 단서) |
| `trades.csv` | 교환 하나 (누가 무엇을 원하고 무엇을 주는지). 같은 NPC도 지역이 다르면 줄이 따로 있다 |
| `items.csv` | 아이템 하나 (레어도 단계, 종류, 얻는 곳, 도감 등록 여부). 도감 칸 `O` 는 아빠의 수첩에 물건 쪽이 있다는 뜻 |
| `notebook.csv` | 아빠 수첩과 아이 기록의 한 줄 (`기록갈래`로 구분). 알게되는키는 웹 코드의 `learn()` 이름 |
| `heirlooms.csv` | 가보 하나 (깨어나는 지역, 깨우는 NPC, 가공법, 숨은 가공품, 손버릇과 손맛 수치) |

| `stock.csv` | 교환 화면의 흔한 물건 하나 (지역, NPC, 내놓는 물건, 한 번에 주는 개수, 바꿀 수 있는 횟수). 값은 레어도로 정해져 표에 적지 않는다 |
| `haggle.csv` | 흥정 반응 하나 (NPC, 지역 또는 전체, 방식 허세·사정·칭찬, 반응, 아이 대사, 대답) |
| `bosses.csv` | 전투 하나 (보스, NPC 전투). 통과 조건과 달래기 |

| `decisions.csv` | 대장 확인 없이 쓰는 결정 하나 (D 번호, 분야, 상태, 출처, 코드 표시, 되돌리는 법). 코드에는 `// 결정 D-xx: …`로 표시한다 |
| `tuning.csv` | 필드 조작·상호작용 거리·꾸벅이 졸음·자동 저장의 수치 하나 |
| `music_layers.csv` | 마음 상태 음악(D-37·D-87)의 곡 하나: 템포 단계, 바탕·그리움·북 층에 넣을 성부 id(+로 잇기). 곡의 모든 성부가 꼭 한 층에 있어야 빌드된다 |

## 규칙

- **표를 고친 뒤에는 웹 게임 데이터를 다시 만든다**: 레포 맨 위 폴더에서 `node prototypes/web/tools/build-data.js`. 아이템·보스 부위·진정수치·가공법·수첩·미니게임·조작감·시간 수치는 웹 게임이 이 표에서 읽는다 (`prototypes/web/js/data/tables.js`).
- **가공법**(heirlooms.csv)과 **진정수치**(bosses.csv)는 `이름 숫자` 모양으로 적는다. 여럿이면 가운뎃점(`·`)으로 나눈다. 예: `쌀가루 2 + 팥 1 → 팥시루떡 1 · 메밀가루 2 → 메밀떡 1`, `싸리버섯 50 · 꾀꼬리버섯 50`. 이름은 items.csv의 이름과 같아야 한다. 진정수치는 선물 하나를 건넬 때 진정 게이지(100이 가득)가 오르는 양이다.

- **id는 영어 소문자이고 바꾸지 않는다.** 다른 표가 id로 서로를 가리킨다. 예: `npcs.csv`의 지역 칸 `dolneomeo`는 `regions.csv`의 `dolneomeo` 줄이다. 화면에 나오는 이름은 `이름` 칸에서 마음대로 바꿔도 된다.
- `regions.csv`의 `구역`은 기존 구역의 `id:이름`을 `|`로 구분한다. 이름 안의 `·`는 그대로 둔다. 웹은 생성된 `TABLES.ZONES`에서 이름을 읽고, 길의 연결은 기존 지역 코드의 출구·문을 따른다.
- **상태 칸**은 기획 문서와 같은 세 가지만 쓴다.
  - `확정`: 정한 것
  - `제안`: 아직 확인이 필요한 것
  - `미정`: 열린 질문
  - `decisions.csv`만 따로 `확정`(대장이 정함)·`채택`(개발자가 정해 쓰고 플레이하며 고침)·`대체됨`(뒤 결정으로 바뀜)을 쓴다. `코드 표시`가 `있음`이면 코드에 그 번호 표시가 적어도 한 곳 있어야 한다. 웹 게임 데이터(`tables.js`)에는 들어가지 않는다.
- 칸 안에서 여러 개를 적을 때는 가운뎃점(`·`)으로 나눈다. 쉼표를 써도 되지만 엑셀이 알아서 따옴표를 붙인다.
- 레어도 단계는 1부터 5까지 숫자로 적는다. 표시 이름은 순서대로 하품·중품·상품·최상품·천하일품이다 (대장 답 2026-10-30, 다섯째 이름은 개발자 안). 기존 나뭇잎·열매 표시는 유지한다.
- items.csv의 `종류`는 `레어도단계` 바로 뒤에 적고, `재료`·`먹을거리`·`도구`·`귀한 것` 중 하나를 쓴다. 보따리에서 찾을 때를 기준으로 나누며, 종류 분류의 상태는 **제안**이다.
- items.csv의 `진행보호`는 `지역id:기존 G.f 완료표시:필요수량[:대체재묶음]`이다. 여러 용도는 `·`으로 나누고, 같은 지역·완료표시·묶음이면 대체재 중 하나만 필요하다. 묶음을 생략하면 각각 필요하다. `ended`는 해당 지역 종료를 뜻한다. 웹은 현재·이후 지역의 미완료 용도와 가공법을 읽어 선물 전후의 부족 수량을 비교한다. 완제품이 있으면 그 재료를 중복 확보하지 않으며, 가공 횟수는 필요량을 결과 수량으로 나눈 뒤 올림한다. 이 보호 방식은 제안이다.

## 미니게임과 조작·시간 수치

`minigames.csv`와 `tuning.csv`는 세로로 긴 표다. 한 줄은 `id`로 식별하는 값 하나이며, `미니게임` 또는 `분류`로 필터를 걸고 `값` 칸을 고친다. `값이름`은 읽기 쉬운 이름, `단위`와 `설명`은 적용 방법이다. 현재 웹에서 옮긴 값은 모두 **제안**이다. 꾸벅이의 졸음은 `tuning.csv`, 다른 미니게임과 아이템별 채집 판정은 `minigames.csv`에 있다.

웹은 초당 60번 규칙을 갱신한다. `프레임`은 이 갱신 한 번이며, `px`는 웹 필드 좌표 단위다. `%p`는 백분율의 차이, 판정 반폭은 기준 양쪽에 각각 허용하는 폭이다. 초·ms로 적힌 값은 실제 시간이다. Godot에서 새로 구현할 때도 단위와 비교 경계를 함께 참고한다. 낮밤은 시간 경과가 아니라 숙소에서 쉬는 행동으로 바뀌므로 주기 수치를 두지 않는다. 시간제한 없는 몸짓 읽기와 재도전 방식은 지역 시나리오를 따른다.

생성기는 필수 id 누락, 빈 칸, 숫자가 아닌 값, 중복 id, 잘못된 상태·부호·정수 단위와 어긋난 판정 범위를 검사한다. 몸짓·장단의 단계 수는 이미 구현된 선택지·노트 시각 목록 안에서만 줄일 수 있다. 새 단계나 값 종류를 추가하려면 웹 코드와 생성기의 필수 id 계약도 함께 고친다. 웹 출력은 `TABLES.MINIGAMES`와 `TABLES.TUNING`이며, 기본값을 코드에 따로 두지 않는다.

교환 재료·보상 수량은 웹에서 각 지역 코드의 `Rg.trade`(교환 화면의 부탁)와 대화 함수가 아이템 id로 다시 적는다. `trades.csv`는 그 수량의 원본 목록이며, 표를 고쳐도 웹이 저절로 바뀌지는 않으니 코드와 함께 고친다(Godot에서는 표를 바로 읽게 새로 짠다). 흔한 물건(`stock.csv`)과 흥정(`haggle.csv`)은 웹이 표를 바로 읽는다. 위치·색·그림 프레임은 코드에 남는다. 전투 변신 손(속도·대기·범위, 산양 피해 배수, 수리부엉이 예고, 고라니 무적)과 곡괭이 부위 피해, 필드 변신 능력(`form_*`)과 낯선 손님 교환 횟수(`stranger_trade_limit`) 등 조절 수치는 `tuning.csv`를 읽는다. 대사와 지역 채집 설명에 쓰인 숫자는 자동으로 바뀌지 않으므로 기획 수치를 바꿀 때 문구도 함께 확인한다.

## 가보 가공과 좋아하는 맛 (PA-43 2단계)

2단계에서는 기존 진행용 가공법 8개와 습득 조건·보상을 유지하면서 선택 가공법 8개를 더했다. 새 가공품의 이름·수량·취향은 개발자 결정이며, 종전 표의 상태는 유지했다. 레어도 표시 이름은 3단계에서 위 결정으로 바꿨다. 가공법 목록은 `heirlooms.csv`, 재료·가공품 목록은 `items.csv`에서 관리한다.

`heirlooms.csv`의 `선택가공품`과 `숨은가공품`에는 같은 줄의 가공법에 있는 출력 아이템 id를 적는다. 여러 개면 `·`으로 나누며 숨은 가공품은 선택 가공품에 포함한다. 숨은 가공법은 목록에서 가려지지만, 깨어난 가보에 정확한 재료를 직접 넣어 만들 수 있다. 발견하면 `recipe:<출력id>`를 배우고 이후 아는 가공법에 표시한다. 종전 메밀떡은 계속 모락의 `morak:memiltteok` 귀띔이 있어야 한다. 가족에게 배운 가공법, 동물의 귀띔, 직접 넣어 보는 발견의 세 경로를 구분한다.

`손버릇기록`은 처음 가공한 가보의 기록이며, `손버릇키`는 `habit:<가보id>`다. 아이의 손버릇·숨은 가공법은 아빠의 수첩의 손버릇·숨은 가공법 장에 아이 글씨로 나온다. 가보 이름은 가보 표에서 읽고, `items.csv`에 같은 가보를 중복 등록하지 않는다. 기존 `crafted_<가보id>` 표시와 저장 키는 유지하고, 새 기록·발견에는 기존 `learned` 배열을 쓴다.

손맛 수치는 `TABLES.CRAFT`로 변환한다. `손맛횟수`는 입력 횟수, 나머지 `ms` 칸은 실제 밀리초다. `손맛간격ms`는 절구의 기준 박자 간격, `손맛여유ms`는 기준 시각 양쪽의 허용 시간, `손맛쉼ms`는 세 번 찧은 뒤 쉬는 시간, `손맛김ms`는 시루의 김이 오르는 기준 시각이다. `손맛끌기px`는 약연의 앞뒤 입력 한 번으로 세는 화면상 끌기 거리(px), `손맛회전도`는 맷돌 입력 한 번으로 세는 원호 각도(도)다. 기존 조작을 그대로 옮겨 약연은 24px 이상, 맷돌은 90도 이상 움직였을 때 한 번으로 센다. 각도는 1~180도, 끌기 거리는 양의 정수이며, 쓰지 않는 칸은 0이다. 박자 오차의 절댓값이 여유 이하이면 맞춘 것으로 보므로 경계값도 포함한다. 예를 들어 간격 650ms, 여유 280ms이면 기준 650ms에서 370~930ms가 같은 판정이다. 이 판정은 소리와 혼잣말만 바꾸며 물건·개수·호감에는 영향을 주지 않는다. 프레임 수·그림 좌표·색을 이 수치와 섞지 않는다.

가공은 잠든 가보·잘못된 조합·수량 부족·선택 가공 후 진행 재료 부족을 확인한 뒤 시작한다. 맞지 않는 조합은 `틀린조합반응`을 보여 주고 재료를 돌려준다. 유효한 가공의 시작 입력에서 재료 소비·결과 지급을 한 번 확정하므로 손맛 도중 창 닫기나 지역 변경이 결과를 없애거나 다시 지급하지 않는다. 연속 입력은 같은 가공을 중복 실행하지 않는다. 탭을 떠나거나 움직임 줄이기를 켜도 손맛 결과로 실패·손실을 만들지 않는다. 기존 진행용 가공은 재료와 보상을 바꾸지 않고, 새 선택 가공만 `items.csv`의 미완료 진행 수량을 더 부족하게 만들지 않는지 비교한다.

`tastes.csv`는 `id,누가,무엇,반응종류,반응대사,효과,상태` 순서다. `누가`는 NPC·전투 상대 id, `무엇`은 아이템 id다. 같은 인물·물건 조합은 한 줄만 둔다. `반응종류`는 `아주 좋아함`·`좋아함`·`그저 그럼`·`싫어함` 중 하나다. 싫어해도 호감이나 진정이 내려가지 않는다. `효과`는 `none` 또는 `calm:1~100` 형식이며, 진정은 전투 상대가 좋아하는 선물에만 쓴다. `TABLES.TASTES[누가][무엇]`에서 `kind`·`line`·`effect`를 읽으며, 공통 조회 함수 `tasteOf(who,item)`를 필드 대화와 전투 선물에서 함께 쓴다. 좋아하는 선물의 기록은 기존 `like:<인물id>:<물건id>` 형식이다. 기존 `bosses.csv` 진정수치는 유지한다. 인물 사연은 공통 조회 결과와 배운 `like:` 키를 조건으로 쓸 수 있으며, 표의 효과가 사연 장면을 자동 실행하지는 않는다.

현재 지역에서 만든 선택 가공품 또는 그림은 `sendHomeGift(regionId,itemId)`로 까치 편에 보낸다. 물건은 1개를 소비하고 그림(`itemId=null`)은 소지품을 소비하지 않는다. `home:<현재 지역id>`로 중복 발송을 막으며, 답장은 다음 지역의 첫 쉼터나 까치 길손에서 한 번 보여 준다. 글은 보낸 지역의 `Rg.homeReply`가 정하고 아빠의 수첩의 까치 답장 장에서 다시 읽는다. 보내지 않아도 진행할 수 있다. 필수 약 보내기와 지역 사연의 기존 조건·보상은 유지한다.

## 기록 갈래 (PA-43 3단계)

`notebook.csv`의 `기록갈래`는 `아빠 수첩`·`관찰`·`손버릇`·`숨은 가공법`이다. 기록은 아빠의 수첩 한 권이다 (대장 결정, PA-46). `아빠 수첩` 줄(쓴이 아빠)과 `관찰` 줄(쓴이 나)은 같은 쪽id의 한 쪽에 위아래로 나오고, `손버릇`·`숨은 가공법` 줄은 수첩 안의 같은 이름 장에 나온다. 기존 행 id와 `알게되는키`, 저장의 `learned`는 유지하므로 옛 저장에서 배운 기록도 같은 키로 열린다. 기록을 모아야 진행하는 조건은 없다.

새 교환 전용 재료는 `trades.csv`의 `t_craft_` 행에서만 얻는다. 현재 지역 대화는 거래 수량을 직접 정하므로 CSV만 바꿔 기존 교환 덤에 붙일 수 없다. 이번 작업에서는 선택 교환 목록과 검증만 추가했으며 실제 메뉴 연결은 지역 작업에 넘긴다. 쌀 8개와 기존 거래 조건은 바꾸지 않는다. 추가 교환은 표에 적힌 여분 채집물을 쓰고, 필수 진행용 수량을 먼저 남겨야 한다. 한 번뿐인 공급량으로 모든 새 가공품을 만들 수 있는지는 별도로 계산하며, 부족한 채집 자리를 확보했다고 가정하지 않는다.

생성기는 BOM, 중복 id·머리줄, 아이템 참조, 양의 정수 재료·결과 수량, 겹치는 가공 조합, 숨은 가공품·발견 기록, 손맛 수치 범위, 취향 대상·효과를 검사한다. 새 선택 가공품의 레어도가 재료의 최고 레어도보다 높으면 생성하지 않는다. `tables.js`는 생성 결과이며 직접 고치지 않는다.

## 교환 화면 (stock.csv · haggle.csv)

교환은 웹 `engine/trade.js`의 "보따리 펼치기" 화면에서 한다 (결정 D-39·D-40). 상대 쪽에는 두 가지가 나온다.

- **부탁**: `trades.csv`의 이야기 교환. 무엇을 원하는지는 각 지역 코드의 `Rg.trade[npc]`가 아이템 id로 다시 적는다. 수량은 `trades.csv`와 같게 둔다. 상대가 원하는 것을 말해 준 뒤(장부에 적힌 뒤)에만 보인다.
- **흔한 물건**: `stock.csv` 한 줄이 하나. 칸 순서는 `id,지역,NPC,물건,개수,횟수,상태,비고`다. `물건`은 아이템 이름이고, 귀한 것과 도구는 쓸 수 없다. 값은 따로 적지 않는다. 같은 레어도 단계 하나, 또는 한 단계 아래 둘이면 바꿔 준다. 하품은 하품 하나로 바꾼다. 상대가 `tastes.csv`에서 좋아하는 물건은 한 단계 위로 친다.

`haggle.csv`는 `id,지역,NPC,방식,반응,아이대사,대답,상태` 순서다.
- `방식`은 허세·사정·칭찬 중 하나이고, `반응`은 좋아함·그저 그럼·싫어함 중 하나다.
- NPC마다 세 방식 모두에 `지역=전체` 줄이 있어야 한다. 지역 id를 적은 줄은 그 지역에서 전체 줄보다 먼저 쓴다(날쌘의 지역별 허세).
- 대사는 화면 아래 한 줄로 나오므로 줄바꿈 없이 적는다.
- 좋아함이면 흔한 물건 덤 하나가 붙는다. 흔한 물건이 없는 상대면 호감이 하나 오른다. 지역 코드가 `Rg.onHaggle`로 따로 맡으면 그 덤이 대신 붙는다.
- 싫어함이면 그 지역에서 그 상대와는 흥정만 닫힌다. 값은 그대로다.
